# 管线细节：节点语义、握手规则、踩坑记录

## 一、第一原则：工作流是变量，节点号不是常量

用户会改工作流（加三采、换超分尺寸、改输出前缀、重排节点）。所以本技能**不存节点号，
只存"角色"**，每次开工由 `h3wf.py` 从 **ComfyUI 最近一次成功执行的图**（`/history` 里的
`prompt[2]`，API 格式）里现场识别：

| 角色 | 识别规则 | 用途 |
|---|---|---|
| `rack` | 类名含 `MediaRack` 且输入有 `rack_data` | 素材架（每段参考图） |
| `desk` | 类名含 `Desk` 且输入有 `desk_data` | 导演台（提示词正文 + 工程名） |
| `cast` | 类名含 `Cast` 且输入有 `h3_data` | 执行台（帧长/续接/纯视觉模式） |
| `seed` | 类名含 `KSampler` 且输入有 `seed`；多候选时取负条件来自 `cast` 的那个 | 重抽只改它 |
| `take1` | 从 `seed` 顺流而下第一个会写文件的合成节点 | 一采前缀；`watch`/`gate --latest` 只认它 |
| `superres` | 类名含 `SuperResolution` | 只记录，不动线 |
| `interp` | 类名含 `RIFE` / `Interpolation` | 只记录，不动线 |
| `collector` | 类名含 `LatestFilmPath` | 三采成片收片器（可选） |
| `adopt` | 类名含 `ProducerClipAdopt` | 段尾归位（可选，但成片回不回导演台看它） |
| `final` | 会写文件（有 `文件前缀`）且输出端口**无人引用**的合成节点 | 终片 |
| `prefinal` | 从 `superres` 的视觉输入往上游找到的最近合成节点 | 终片无声时的音轨来源 |

握手还会记两样东西，`submit` 直接依赖它们：

- `chain.name`（导演台工程名）→ 决定成片归位到 `h3_chain/` 的哪个目录。
  读不到时 `submit` 会退回技能工程名并告警 —— **那等于另起一部片子**，续接必然断。
- `take1_prefix`（一采的文件前缀）→ `watch` 只在新落盘的「一采」里找文件。
  没有它就只能按 mtime 取最新，完整链跑完时最新的永远是超分/终片，双检对象全错。

`submit` 只做三件事：把 `rack_data/desk_data/h3_data` 三个 JSON 换成当前段的内容、改 `seed`、
提交。**一律不碰连线**。

> 历史教训：v2 里写死"306 超分把视频口删掉、图像口改接 285；308 补接 286 音轨"。
> 到 1018 版工作流时，超分本来吃的是三采合成（298），终片音频本来就有 —— 那段"修复"
> 反而把好链路改坏了，表现为每次提交都报错。**这就是不再做接线手术的原因。**

## 二、实测链路（`minimax h3-三采-1018-收片归位`，仅作参考，不作依赖）

```
一采   280  banzhangVideoCombine(一采)        ← 275 VAEDecode / 276 VAEDecodeAudio
二采   304  banzhangVideoCombine(二采)        ← 285 二采解码 / 286 二采音频
三采   298  banzhangVideoCombine(三采)        ← 296 三采上采样 / 295 三采音频
超分   306  RTX SuperResolution 1920×1080
终片   329  SaveVideo(班长作品)               ← video 306:1
收片   327  H3_LatestFilmPath(三采_N298)      ← 325 净化·信号直通出口
归位   328  BanzhangProducerClipAdopt         ← 成片 327:0，顺序锚 261:3
```

要点（都是实测踩出来的）：

- **超分出来的 1080p 文件没有音轨**，哪怕 306 的「保留原音 = 开」。原因是它的「视频」输入接的是
  298 的「🎬视频透传」，而图像编码模式下那个口恒为 `None`（坑 #1）。所以 `finish` 必须从
  298（prefinal）取音轨来 mux，不能指望终片自带。
- **终片用 `SaveVideo`（输出节点），不要用 `banzhangVideoCombine` 接超分**：
  combine 的 `_resolve_video_path` 只认「`get_stream_source()` 返回真实文件」的 VIDEO，
  超分给的是 comfy_api 的 `VideoFromFile`（临时文件已回收），接上去必报"未接入视频文件"。
  307 RIFE 能接是因为它自己流式编码并持有文件；砍掉插帧后 308 就断了。
- 二采（304）在这条链上**不参与终片画面**，它只是过程中的中间检查点。QC 只认一采前缀。
- 是否三采、几档放大、插帧开不开，全看用户当天的工作流；技能不预设。
- `307 RIFE`、`308 combine`、`273 SLA` 在图里被 bypass（mode=4）但节点保留 ——
  要 48fps 或换大显存卡时把 mode 改回 0、把 308 的视频口接回 307 即可。

## 三、段间续接的真正机制

执行台只在 `h3_data.cont.latent_file` **非空**时才走续写，否则把本段当第一段（画面不接上一段）。
所以续接是三个条件同时成立：

1. **`cont` 有开关 + 窗口**：`{mode:"latent", frames:39, latent_file:<路径>, latent_video:<成片相对路径>}`。
   `frames` 是承接窗口，`latent_file` 只当开关用（执行时按 chain 记录找真实档）。
2. **同一 `chain.name`**：上一段和本段必须在同一个 `h3_chain/<工程名>` 里。
3. **本段已在 `chain.order` 里，且位置在上一段之后**：执行台用 `order[k-1]` 找上一段，
   找不到（k=-1）就退回「全局最新的续拍存档」—— 那就是串工程。

`sop_run.py submit` 因此**在提交前**调 `/cglide/chain/add_clip` 登记本段、拿到段落 id，
再 `GET /cglide/chain/cont?name=&id=<上一段>` 取它的 cont 路径，写进 `h3_data.cont`。
同 `shot` 重复登记会复用原段，重抽不堆段。

**由此推出一条硬约束：同一任务全程只能用同一个 `chain.name`。**
上面三个条件里，2 和 3 都挂在 `h3_chain/<工程名>/` 上：换名字 → `order` 空了 → 本段 k=-1 →
退回「全局最新存档」或直接当第一段。所以 `project.json.chain` 记录绑定，`submit` 每次比对，
不一致就拒收（`--chain` 用回原名 / `--rebind` 明确换工程）。详见 SKILL.md §10.1。

- **别把整片所有段堆进 `desk.segs` 一次提交**：H3 一次只生成 `cur` 那一段，其余段不会跑。
- 正确做法：每段 `cur=<seg>`、`segs` 只含本段（`submit` 已按这个生成）。
- 跨段角色一致性主要靠素材架参考图 + `subject_definitions` 里内联特征，不靠 latent 续接；
  续接管的是**头 5 帧的状态锁定**（站位/道具/光线，v3.8：钉帧后被 concat 裁头收回，
  所以它锁的是物理状态、不进成片），不是长相，也不进交付画面。
- 第一段：`cont={}`，`trim_frames=0`（`add_clip` 在 order 为空时自动给 0），不承接任何段。
- 某段要断开（换场/闪回）：v3.8 起尽量**不用** `--cont off`——跳转段照常续接，头 5 帧
  裁掉即净；`--cont off` 只留给第一段和诊断对照（见 SKILL.md §4）。仍用时的口径：
- **`--cont off` 的段也必须记 `trim_frames=0`**（头部没有承接帧，组装时不能裁）。
  但它不是 `order[0]`，`ensure_clip` 每次重抽都会把它压回工程默认值（5 或 39）——
  所以组装时必须按「cont off 段头不裁」**手传参数**，别信档案里的记账。
  要修档案就 `POST /cglide/chain/update {"name": <工程>, "id": <clip_id>, "patch": {"trim_frames": 0}}`。
- 续接钉帧（`project.json` 的 `cont_frames`）建议 **5**（0.21 秒）：足够锁机位/光线/色彩与姿态大致接续，
  又不浪费净新画面。39 帧（1.625 秒）会把一段的 1/4 花在重绘上一段的尾巴上。
  **净新画面 = length − cont_frames**，175 帧配 5 帧 = 170 帧（7.08s）可用。

### 段尾归位：让成片真的回到导演台

症状：跑完以后 `h3_chain/<工程名>/` 里没有 mp4、`_preview.mp4` 是 0 字节、`shot_versions`/`files`
表为空 —— 归位节点没执行，或执行了但「成片」口没拿到文件。

标准接法（缺一段都不成立）：

```
298 三采合成 ──🎬视频/图像透传──> 🧹 净化 325 ──信号直通出口──> 🎬 三采成片收片器
                                                                  │ 三采成片路径
                                                                  ▼
261 导演台 ──总帧数(slot 3)──────────────────────> 📦 段尾归位 .顺序锚
                                                   📦 段尾归位 .成片 ← 收片器
```

- 收片器参数用默认值：`文件名前缀 = 三采_N298`（= 298 的「文件前缀」+ `_N` + 节点号），
  `秒数窗口 = 600`。它扫 `output/` 取窗口内最新的匹配文件，输出**绝对路径**字符串；
  归位的 `_resolve_video_input` 正好认绝对路径（`os.path.isfile` 直接通过）。
- **顺序锚必须接导演台「总帧数」，不能空**。归位靠 `cm.last_name()` 读 `h3_chain/_last.json` 定位工程，
  而该文件由导演台执行时 `mark_last()` 写入。锚点空着 → 归位可能在上一个工程的上下文里跑 → 成片串档。
- **触发口别接 298 的「🎬视频透传」**：图像编码模式下该口恒为 None（坑 #1）。接净化节点的
  「信号直通出口」既保证 298 已落盘、清理已完成，又不会让 294 帧的图像 batch 被引用常驻内存。
- **成片口别接终片 308**：插帧后是 48fps/588 帧的内存流、没有磁盘文件，硬接会让导演台按 24fps
  算出双倍时长。要的是三采那版 1248×704/24fps 的段落片。
- 只跑三采（超分/插帧静音）也能归位 —— 这正是收片器存在的意义。

自检：`h3_chain/<工程名>/` 是否新增 `clip_NNNN.t<take>.mp4`；`project.db` 里 `shots.meta_json`
的 `film_frames` 是否等于段帧数（例如 294）。归位自带幂等：目标成片已存在时只补续拍档、不重复覆盖。

## 四、schema 速查

```jsonc
// rack_data（素材架）
{ "slots": {"images":[],"videos":[],"audios":[]}, "fps":0, "audio_out":0,
  "cur": "seg01",
  "segs": {"seg01": {"slots": {"images": [{"file": "cglide/<项目>/角色1.png",
                                            "alias": ["角色1"]}], "videos": [], "audios": []}}} }

// desk_data（导演台）
{ "chain": {"name":"<工程名>","clip":"<已登记的段落id>","shot":"seg01"},
  "global": "", "segs": {"seg01": "<H3 提示词全文>"}, "alias": false, "presets": [] }

// h3_data（执行台，submit 只改这四处）
{ "chain": {"name":"<工程名>","clip":"<已登记的段落id>","shot":"seg01"},
  "length": 243, "prompt": "",
  "cont": {"mode":"latent","frames":39,
           "latent_file":"h3_chain/<工程名>/clip_0003.t6.cont.safetensors",
           "latent_video":"h3_chain/<工程名>/clip_0003.t6.mp4"} }
```

- `chain.clip` 必须是**已经在 chain.order 里的段落 id**（`submit` 会先 `add_clip` 拿到它再写）。
  写成段名（`seg01`）执行台认不出来，会退回"全局最新存档"续接 —— 串工程。
- 第一段 `cont` 给 `{}`；要断开也给它 `{}`。
- `@图片N` 的 N = 该段 `images` 数组顺序（从 1 起）；`alias` 写角色名，正文里也用角色名。
- `length` 必须落在 17k+5 网格：124 帧≈5.17s、243 帧≈10.13s，画布 576×320（ref2va）。
- 纯视觉静音段：`h3_data.mode = "anullsrc"`（`submit --silent`）。

## 五、踩坑记录（仍然有效）

| # | 坑 | 结论 |
|---|---|---|
| 1 | 合成节点的「视频透传」口 | 只有输入是 VIDEO 文件时才透传；图像编码模式下返回 None。别指望从图像编码节点取视频流，也别拿它当收片器的触发（见上一节） |
| 2 | 执行台的「整片」输出口 | 从磁盘档案读累积全片（依赖片名 + 段尾归位机制）；API 单段直跑时可能输出 None |
| 3 | `prompt_id` 归属 | 判归属只看 `/history/<prompt_id>.outputs`，或"提交前基线的增量"。按 mtime 取最新会抢到别人的片子 |
| 4 | `Counter` 复用 | 反复运行会写同名递增文件（`一采_N280_0162.mp4`）。文件名不是唯一键 |
| 5 | 解释器 | 必须用 venv python（cv2/numpy 在里面），系统 python 跑 `sop_check` 会 ImportError |
| 6 | seed | 主线只在主 `KSampler`（现为 277）；放大/三采的种子是固定值，重抽不改它们 |
| 7 | 参考图水印 | 素材角落可能有 "Seko" 水印 → 防错约束必写「忽略参考图水印、画面无文字字幕」 |
| 8 | 身份漂移 | `@图片` 锁定不可靠（实测 5 次里出现发型/衣服/年龄漂移）→ `subject_definitions` 内联可见特征 + 否定项；正文节拍只写衣物随动 |
| 9 | 代理劫持 | `HTTP_PROXY` 会把 127.0.0.1 变成 502 → `paths.http_json` 统一用无代理 opener（已内置） |
| 10 | `audio_gate --out x.mp4` 的画面来自 `--in` | 它不会把音轨接到超分画面上。交付必须"先出 wav 再 mux 到终片"，`finish` 已按这个实现 |
| 11 | 分辨率两档 | 二采 864×480、终片 1920×1080。混分辨率 `-c copy` 会失败 → `concat` 自动切重编码分支 |
| 12 | 直方图突变 ≠ 失败 | 段内多镜头硬切本来就会触发。拿突变时刻去对段规划的切点，对上就是正常 |
| 13 | 超分节点不是"终片" | 它吐的是内存里的 `VideoFromFile`，`banzhangVideoCombine` 接不上（报"未接入视频文件"）；要落盘就用 `SaveVideo` |
| 14 | 超分"保留原音=开"也会没声音 | 它的视频输入接的是 combine 的「🎬视频透传」，图像编码模式下该口恒 None。音轨要从三采取 |
| 15 | `/history` 重启即清空 | 握手会打 `history_seq` 水位线；比水位线老的执行图不判漂移，避免刚 sync 完就被拒收 |
| 16 | `--cache-lru 1` 不是重算元凶 | 实测一次执行里 47 个节点各只跑一次（导演台也只 1 次）。别为"省算力"去动它，改了只有风险 |

## 六、性能：这台机器的实测结论（别照着直觉改）

RTX 5060 8GB / R5 5600X / 16GB DDR4，模型 19.5GB —— 显存装不下，forward 逐层搬权重。

| 尝试 | 结果 | 结论 |
|---|---|---|
| 修好 SLA 让官方分片内核生效 | 确实挂上了（`已挂上加速：官方分片内核`），但一采 121→128s、二采放大 205/229/231s 无差异，显存涨到 1.9GB | 8GB 卡上是负收益 → 节点 bypass 保留，换 16G 以上卡再启 |
| 去掉 `--disable-pinned-memory` | 跑完物理内存只剩 0.5GB、页面文件 48.6GB，全线慢 10~15% | 16GB 内存扛 19.5GB 模型时 pinned 有害 → 保持 disabled |
| 砍掉 RIFE 插帧（只要 24fps） | 省 145s | 有效，但**终片必须改 SaveVideo 落盘**（308 会断） |
| 换 11GB 的 `ref2va_w4a8` 模型 | 未实测 | 工作流是 ref2va 模式，权重搬运减半，理论上最快；画质需人工看片 |

**规矩**：任何"优化"都要用同一段、同一参数跑完整一条链，对比各节点 `elapsed`；只跑一采
或只看总时长都会被放大阶段的波动骗到。

### 显存回收（2026-10 新增：曾经让一段跑成 33 分钟）

工作流末尾的显存清理节点（`BanZhang_VRAM_Cleaner` 这类）**只在正常跑完时执行**。两种情况让它失效：

1. 中途 `/interrupt` —— 执行链被砍在第 N 步，清理节点根本没轮到；
2. **两段之间提交太快** —— 上一段刚落盘就提下一段，那些重量级清理
   （清文件缓存 / 进程内存 / DLL，`重试次数=4`）还没跑完，新任务已经启动。

此时显存守卫节点（`VRAM_Guard`，预留 1.0GB）判定可用不足 → **每采一步卸载再重载模型**。
6 步采样 = 6 次热加载：`45s/步 → 300s/步`，5 分钟变成 33 分钟。

**识别特征**：日志里 `299.90s/it` 这种量级，或 `Model Initialization complete!` 出现在第 1 步的位置；
`nvidia-smi` 显示 GPU 利用率 100% 但**功耗只有 42W**（正常 81W）—— 这是在等数据，不是在算。

**三个接口别搞混**：

| 接口 | 实际效果 |
|---|---|
| `/interrupt` | 只让采样循环抛异常退出，**模型不动** |
| `/queue {"clear": true}` | 只清未开始的任务 |
| `/free {"unload_models": true, "free_memory": true}` | **只有这个真卸模型** + `empty_cache()` |

顺序必须是 **中断 → 等队列空 → free**（运行期间调 `/free` 会被排到执行结束，等于无效）。
清完残留约 1.7GB 是 CUDA context，正常。

**已内置**：`scripts/gpu_vram.py`（`--check / --clean / --ensure`）。`sop_run.py` 三处中断路径
（快检失败、质检失败、手动 abort）末尾自动 `free(wait=2.5)`；`submit` 在登记段前自动 `ensure_clean()`
（队列空且空闲 <1.2GB 才动手，正常态不误伤，dry-run 跳过）。

### 段尾归位依赖 ffprobe

便携包/网盘里的 `ffprobe.exe` 常是没下完的残片（文件大小远小于声明值，改成 exe 会报
"不是有效的应用程序"）。缺它时官方归位链路会在 `collect_run()` 里硬失败：
`收片后无法确认视频帧数`。两条路：

- 装一个真 ffprobe（放进插件 `tools/ffmpeg/bin/` 或 `PATH`）；
- 启用探帧兜底补丁 `custom_nodes/banzhang_h3_probe_fallback/`（只在官方探测拿不到帧数时介入，
  用 `ffmpeg -i` 的 Duration×fps，再不行数包；写同一份缓存键）。`H3_PROBEFB=0` 可关。

`paths.py` 的 `ffprobe` 字段会如实标「缺失」——`h3proj` 自己走 `ffmpeg -i` 兜底不受影响。

## 七、排程建议

- 按"完整动作/镜头边界"切线，不复刻场次：一场戏常常拆成 a/b 两段（台词一段一句）。
- **串行生产**（单卡）。每段跑完立即 `finish` 归档，别攒到最后一起收。
- 无角色段（空镜/大场面）也要写 prompt：只写场景 + 氛围 + 环境次级运动。
- 单段一次生成通常几十分钟，`watch` 建议后台跑，出结果再读台账。
